# ZAIKO 要件定義書

- バージョン: 0.1
- ステータス: 要件整理中
- 対象: 飲食店向け在庫・発注管理システム

## 1. 開発背景

現在の飲食店業務では、食材の在庫確認や
発注管理を紙ベースで行っている。

特にGW・お盆・年末年始などの繁忙期は、
仕入先の休業日を考慮した発注が必要になる。

また、スタッフのポジション異動により、
過去の発注判断や在庫状況を把握しづらく、
経験豊富な先輩スタッフへの確認が必要になる。

## 2. 開発目的

- 在庫確認・棚卸作業の効率化
- 日次在庫と食材状態の記録
- ロス数量・理由の可視化
- 発注・承認・納品履歴の一元管理
- 経験の浅いスタッフの発注判断支援
- 過去の繁忙期との実績比較

## 3. システム構成

### Backend

- Ruby on Rails 8.1（APIモード）
- Ruby 3.4
- PostgreSQL
- RSpec

### Infrastructure

- Docker
- Docker Compose
- GitHub Actions（CI）

### Frontend

- React Native
- Expo
- TypeScript
- iOS / Android対応

### 認証

- Google OAuth 2.0 + OpenID Connect
- Authorization Code Flow + PKCE
- Rails側でスタッフの認証・認可を検証
- 未登録・無効化スタッフの利用は禁止

## 4. 利用者と権限

### 利用者

- 一般スタッフ
- 発注承認者
- 管理者

### 権限管理

- 基本権限はスタッフマスタで管理する
- 担当ポジションと発注承認権限を分離する
- 異なるポジションでも許可された発注は承認可能
- 承認権限は管理者が明示的に付与する
- 権限がない操作はRails側で拒否する
- 自己承認は原則禁止する
- 権限付与・変更・失効の履歴を保持する

**最終ゴール:**

### FR-02 在庫表出力

- [ ] PDF形式の棚卸表出力
- [ ] CSV形式の在庫表出力
- [ ] ポジション別の出力
- [ ] 保管場所別の出力
- [ ] 対象日を指定した出力
- [ ] 食材名・単位・実数記入欄の出力
- [ ] 食材状態・メモ欄の出力

**最終ゴール:**
棚卸表をPDFで印刷でき、
在庫情報をCSVで集計・加工できること。

### FR-03 棚卸管理

- [ ] 日次棚卸の作成
- [ ] 食材ごとの実測数量入力
- [ ] 食材状態・メモの登録
- [ ] 下書き保存
- [ ] 未確認項目の識別
- [ ] 棚卸内容の確定

- [ ] 同一対象の二重計上防止
- [ ] 同時更新時の競合検知
- [ ] 過去の確定済み棚卸の参照

**最終ゴール:**
日々の実在庫を記録し、
棚卸作業を確実に完了できること。

### FR-04 在庫メンテナンス

- [ ] 権限を持つスタッフによる在庫訂正
- [ ] 確定後訂正時の理由入力（任意）
- [ ] 訂正前後の数量保存
- [ ] 訂正者・訂正日時の記録
- [ ] 不正な数量・単位の拒否
- [ ] 他店舗データの変更禁止
- [ ] 訂正履歴の参照
- [ ] 同時更新による上書き防止
- [ ] 訂正後の集計整合性確認

**最終ゴール:**
誤登録を安全に訂正し、
変更履歴を追跡できること。

### FR-05 ロス管理

- [ ] ロス数量の登録
- [ ] 廃棄・腐敗・破損等の理由登録
- [ ] ロス発生日・記録者の保存
- [ ] ロス履歴の照会
- [ ] 推定使用量の計算に利用

### FR-06 発注管理

- [ ] 仕入先マスタ・仕入先別取扱商品の管理
- [ ] 発注案の作成・編集・途中保存・再開
- [ ] 発注申請、承認・差戻し、発注・承認履歴の照会
- [ ] ポジション横断で依頼を集約し、依頼元ポジション・依頼スタッフ・食材・依頼数量を個別に参照
- [ ] 発注状態・次に必要な対応・対応期限・対応可能なスタッフを一覧で確認
- [ ] 対応期限を過ぎても未完了の場合、現在の対応担当者へ通知。承認待ちは取りまとめポジションの有効な承認権限者全員を通知対象とする
- [ ] 自動承認は行わず、承認権限を持つスタッフが明示的に承認
- [ ] 発注数量の変更理由を選択肢から記録し、仕入価格の比較・変動理由も記録
- [ ] 「その他」の補足は任意入力、100文字以内とする
- [ ] 仕入先へ送信する前の発注に、現場スタッフが明細追加・数量変更・明細取消を提案でき、承認者が採否を判断
- [ ] 承認者は未判断提案がなく、現在の発注内容版が承認済みの場合に限り最終承認できる
- [ ] 承認は発注書の取りまとめポジションに対する有効な承認権限で行い、発注作成者本人は承認できない
- [ ] 発注申請時に承認期限・仕入先への発注期限・送信担当者を確定する。申請後は両期限を必須とする
- [ ] 申請内容を不変の発注内容版として保存し、承認履歴・PDF・FAX送信記録を同じ版番号に紐付ける
- [ ] 発注内容の変更または採用提案の反映で新しい内容版を作成し、以前の承認を無効にして再承認する
- [ ] 明細取消は論理取消とし、依頼・提案・承認履歴を保持する。取消明細は数量集計・PDF・送信・納品照合から除外
- [ ] PDF生成・FAX送信記録の前に、未判断提案なし・現行内容版の承認済み・有効明細あり・未送信を検証する
- [ ] 未判断の提案がある場合は承認・送信を停止し、送信準備中は発注内容の編集・提案受付を停止する。準備を中止した場合は再開する
- [ ] FAX送信済みの手動記録に、送信担当者・日時・送信先・送信した内容版を保持
- [ ] 送信後の発注内容変更・取消は本Issueの対象外とし、通常更新を禁止する。履歴を保持する別処理は後続Issueで設計する

## 7. 開発フェーズ

### Phase 1-A 認証・マスタ管理

Google認証、スタッフ、ポジション、
食材、保管場所の管理。

### Phase 1-B 日次在庫・ロス管理

日次在庫確認、棚卸、
食材状態、ロス記録。

### Phase 1-C 在庫照会・帳票・メンテナンス

在庫照会、PDF/CSV出力、
在庫データの訂正・監査。

### Phase 2 発注・承認・納品

発注案、承認、FAX帳票、
納品・検品、在庫移動。

### Phase 3 分析・発注支援

過去実績、繁忙期比較、
推定使用量、発注支援。

## 8. 開発ルール

- バックエンドを先に実装する
- フロントエンドは後続フェーズで開発する
- Issueに実装範囲と完了条件を記載する
- TDDで実装する
- Gitmoji＋日本語でコミットする
- PRでCodexレビューを受ける
- 必須CIが成功してからマージする
- マージ後は作業ブランチを削除する
- 追加仕様は別Issueで管理する
